# Security model — Stage 2 foundation and Stage 3 live quiz

Frontend: static GitHub Pages; only public Supabase project URL/key and optional CAPTCHA site key. OAuth uses Supabase-managed Google secrets and PKCE, returning to `/el-zhady/`. No service-role key, OAuth secret, database password or admin password is used by browser code. A user's Auth session token is sensitive and is stored by Supabase Auth in this browser for normal refresh recovery; treat the site as any authenticated web application and keep untrusted HTML/scripts out. React escapes display names; no raw HTML rendering is used.

## Data boundaries

- `public.profiles`: permanent account's own row only; no email/admin column. Writes through `save_profile`, always `auth.uid()`.
- `public.practice_results`: permanent account's own rows only; 5 activity IDs, each capped at 20. Browser has no write grants. Not yet populated by real gameplay.
- `public.rooms`, `public.room_participants`, `public.competition_results`: only permitted room members and authorised admins can read. Result owners with registered membership may also read their own historical result. These tables contain safe lobby fields, never Auth UUIDs/emails. Display-name snapshots preserve guest results independently of future account names.
- `el_zhady_private.memberships`: Auth UUID → participant UUID, room, guest/registered kind, removal flag. Never exposed or published. Unique room/Auth UID prevents duplicate joins. Same-name people have distinct participant IDs and visible suffixes. Identity kind is a join-time snapshot; upgrading an Auth user never retroactively turns a guest result into permanent history.
- `el_zhady_private.admins`: provisioned only through trusted SQL by the project owner. RLS/default deny plus revoked grants prevent student/guest changes. Authority depends on this table AND permanent identity; metadata is never an authority source.
- `el_zhady_private.room_requests` / `join_limits`: idempotency and per-identity quotas; browser cannot mutate them.
- `el_zhady_private.answer_keys`: reserved for future trusted scoring, empty now, no browser access. There is no public answer-key table or RPC accepting client-computed scores. Stage 3 uses separate private quiz tables and a validated answer-ID submission RPC.

Every app table has RLS. Exposed tables grant only SELECT to `authenticated` with restrictive policies; `anon` has no access. Supabase anonymous users use the `authenticated` role, so policies/functions additionally check `auth.users.is_anonymous`. Role name alone never grants registered-user rights. Helpers use security-definer access to avoid recursive RLS on memberships; every privileged function pins an empty search path and qualifies object names. Only required RPC/helper execution is granted. There is no arbitrary SQL/external command RPC.

Supabase's Auth service is the trusted identity issuer. Tests substitute its UID boundary in an isolated PostgreSQL engine; that is not a live Auth/JWT verification test. Do not expose the test bootstrap or private schema on hosted Supabase.

## Mutations and scoring

Joining checks rate, name/code, room status, removal, lock and capacity, under per-user advisory and per-room row locks. Existing active membership can reconnect to a locked/full room; closed rooms reject join attempts. `get_lobby` still lets permitted existing members read a closed room's status/results. Removal revokes future member reads and retry access without deleting stored results. A user already saw prior room data; revocation cannot erase their memory/screenshots.

Failed join errors return typed JSON after updating the quota, so a rollback cannot erase the failed-attempt count. Creating rooms requires an admin, a UUID request ID scoped to that admin, a valid title and an hourly quota. Client persists the request ID/payload before the request; timeout/reload retries reuse it. Lock/unlock/remove/close set state idempotently. Refreshing a lobby fetches existing membership; it never creates a new identity or membership.

Independent practice scoring is absent. Stage 3 live scoring runs only in protected SQL functions, validates identity/membership/question/option/time, reads private frozen keys and writes answers/results. RLS/grants deny even a registered student direct score inserts/updates. Do not implement client-provided scores or publish correct-answer keys. Admins manage rooms, not private student profiles/practice records. Service-role capability must remain outside this repository/frontend.

## Realtime and reliability

Only the safe lobby tables are published. Postgres Changes reads are subject to Supabase authentication and table RLS. Realtime causes a fresh authorised `get_lobby` fetch; the UI does not trust the event as the authoritative room snapshot. The client polls every 15 seconds while visible, refreshes on online/focus and sends a throttled heartbeat every 25 seconds. Recent activity is labelled as activity, not guaranteed online presence. Removed users may miss the removal event after losing RLS access; the next fetch/poll detects denial and clears the lobby. WebSocket/auth refresh/reconnect still needs hosted acceptance testing.

Network/Auth operations have 12-second bounds and readable retry/error states. Public content does not depend on a working backend. Supabase Auth is the only persistence for identities; PostgreSQL is the only persistence for profiles/rooms/results. Existing local preferences, the OAuth destination and admin request tokens are not substitutes for backend data. No local mock backend is used. PGlite is a dev-only SQL test dependency, not browser persistence.

## Deployment and abuse limits

See SUPABASE_SETUP.md. Before public guest usage, configure Auth's anonymous/IP quotas and CAPTCHA on both Supabase and the frontend. Database quotas limit each UID and cannot prevent unlimited identities, coordinated distributed abuse or offensive but syntactically valid display names; hosts can remove participants and lock rooms. No false claim of comprehensive anti-abuse protection is made.

GitHub Pages remains static; only its approved main-branch workflow deploys. The owner has now explicitly authorised Stage 2 merge/deployment after review and passing checks. PR CI and Pages validate all four public build variables without printing their values. No migration is run by the release workflow; the owner reports the initial migration already applied manually. The owner reports Stage 2 provider/profile/admin/guest/locked-room tests passed, including a physical iPhone. Stage 3 hosted migration/Cron/PostgREST/Realtime and physical gameplay still require acceptance; local fixtures are not that evidence.


## Stage 3 quiz security and races

All seven new tables enable RLS. Private authoring/snapshot/roster/answer tables have all browser grants revoked; even a browser admin cannot select them. Safe sessions/results grant SELECT only with room/registered-own-result policies. Only safe sessions/results are added to Realtime. The RPCs never return email/Auth UUIDs, another person's submissions before reveal, future prompts, or future keys. Current-question leaderboards hide current correctness until reveal. Admin review is authorized and limited to revealed ordinals, including after cancellation.

Every public live RPC uses pinned empty search_path and qualified names. Configure/start/cancel/review require a permanent private admin grant. No client can call scheduler/sync/clock/board helpers. Start is atomic under room/session locks and copies immutable roster/content. Answer RPC derives the participant from `auth.uid()` and checks nonremoved membership/frozen roster, server time/current question/stable option. It accepts no scores, timestamps or correctness. Answer primary key and room/session serialization make first acceptance win; retries return that old acknowledgement even if the option differs or deadline passed. Removed users still fail access before duplicate lookup. Finalization locks the session, inserts unique per-session/participant rows, uses correct-count/speed ranking, then sets completed. Repeated ticks/state calls/start cannot reset/duplicate results. Concurrent removal serializes with completion: removing before finalization excludes that competitor; removal after completion does not rewrite historical ranks.

Cron runs as the trusted scheduling database owner and calls only the fixed private tick. No HTTP webhook secret or service key is required. Readiness requires an exact active named same-database job, not just an enabled frontend button; actual Cron execution health must still be monitored. RPCs repair clock-derived state if a tick is delayed. Submission windows do not extend when a browser disconnects. Browser cosmetic clocks are approximate and cannot override the backend deadline. Scores include server/network queuing, so speed is an imperfect fairness signal. Do not treat this as a high-stakes anti-cheating system.

Cancellation retains private answers without inserting completed results. Guests retain identity-kind/name snapshots and never receive permanent-account results through name similarity or later upgrading; registered history also checks frozen roster kind. Practice tables are never written by live quiz logic. Existing Auth/CAPTCHA/join validation/UID quotas/capacity remain in force. Public repository SQL is not secret; private API keys/projections do not prevent a determined reader inspecting seeded correct answers. Development test transport/clock/Auth fixtures are outside the application bundle, bind only local isolated services and must never be deployed as a backend.


## Competition lifecycle/reveal amendment (draft)

The new private `blocked` flag is scoped to membership/Auth UID + room; display names, emails and new anonymous identities are never ban keys. Existing permanent-removal rows migrate as blocks. Temporary removal requires explicit rejoin before first competition start; reads/heartbeat never reinstate membership. A persisted started timestamp and fixed competition roster deny fresh/removed joins between rounds. Every manual round start names its target, preventing delayed start retries from accidentally advancing.

Both raw score tables (`competition_results`, `live_quiz_results`) now have ADMIN-only SELECT RLS and leave Realtime publication entirely. The new safe competition metadata enters Realtime. Player access is only current question + own accepted answer, reveal-time own per-question feedback, and—after host final publication—the shared top-three tied groups plus own final result. All player full-leaderboard fields are empty, including legacy lobby RPC results and direct table queries. Registered history is withheld until reveal or final closure; unrevealed closed archives omit rank. Admin reports remain reveal-gated per question. No future question keys or opponent submissions are public.

New room/competition/session lock order serializes lifecycle changes. Existing receipt-time score math/first-answer-wins logic is preserved in a private compatibility helper and wrapped by competition completion handling; the sync entrypoint is replaced in place for existing SQL callers. A one-second Cron tick never starts the next game or reveals final results automatically. Final publication is an admin-only idempotent timestamp. Browser animation is presentation only; reloading renders already-published results without replay.

Closed-room checks apply on initial reads and reconnect, so the client returns home via an explicit server-closure navigation path even if a live leave guard exists. Permanent deletion requires closed state and admin authority. Completed score/name snapshots are archived in RLS/default-deny history without room/session/participant FKs before room-scoped records are physically removed. Registered ownership is derived from BOTH frozen/join-time kinds, never a name. Guest archive rows have no registered UID. User accounts/profiles/practice records are never deleted. Minimal retired code tombstones invalidate old QR codes permanently; creation request IDs/quota ledger retain null room pointers after deletion so retries cannot recreate rooms.

No migration/Cron setup was run on hosted Supabase. New migration refuses active Stage 3 games and must be applied during coordinated maintenance with the matching frontend release; see COMPETITION_SETUP.md. All old applied SQL files stay unchanged. Mixed game scoring remains rejected pending a reviewed normalization/weight/speed/tie policy. Public SQL seed visibility and new-guest-identity evasion remain candid limits, not solved anti-cheating/moderation guarantees.
